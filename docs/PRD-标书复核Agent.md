## 1. 产品定位

### 1.1 一句话定位

> **在 smartchat 的企业知识问答能力之上，新增一条"标书复核"业务链路：上传招标文件 PDF，自动提取全部应交材料与资质，生成左右对照的复核界面（左原文/右清单/可定位高亮），并自动检索企业知识库填充"我方是否具备"，最后导出成表。**

### 1.2 目标用户与场景

| 项 | 说明 |
|---|---|
| 用户 | 企业内部**备标人员**（招投标业务人员，非技术人员） |
| 场景 | 收到招标文件 → 备标准备 → 截止前核对材料是否齐全 |
| 痛点 | 招标文件几十上百页，材料要求散落在 6 类章节里；**漏一份声明函 = 废标**，之前投入全部沉没 |
| 现状替代方案 | 人工逐条比对，耗精力且易错；或直接把 PDF 丢给通用大模型，**但模型会编页码、会漏项、会添加原文没要求的内容** |

### 1.3 核心价值（按优先级）

1. **准确**——不能少、不能多、不能错（这是产品的唯一硬指标）
2. **可溯源**——每条清单都能一键跳回原文并高亮依据
3. **省力**——把"逐页找要求"变成"过一遍清单"
4. **可交付**——产出能直接发给同事/存档的成果物

### 1.4 对外口径（面试用，与内部目标分开）

> "给企业内部备标人员用的材料清单复核工具。上传招标文件 PDF，自动提取应交材料和资质，生成单文件离线 HTML，左侧原文右侧清单，点条目跳转高亮——防漏交导致废标。"

⚠️ 口径边界：**不说"产品"、不说"平台"、不说"多用户"**。定位就是内部工具，一期单实例。

### 2.3 差距分析：二开要补的就是这四件事

| # | 缺口 | 现状 | 二开目标 |
|---|---|---|---|
| **G1** | Python 管线是**命令行脚本**，不是服务 | 手动 `python build_review_html.py --pdf ... --items ...` | 包成 HTTP 端点，由前端上传触发 |
| **G2** | 流程**割裂**：提取靠人（AI 和我）产出 items.json，管线只负责渲染 | 需要人工准备 items JSON | **用 FC 引擎自动提取**，产出 items JSON |
| **G3** | **无知识库联动**：清单出来是空的"我方是否具备"列 | 靠人回忆/翻资料 | 自动 `searchRag` 检索历史资质业绩填充 |
| **G4** | **不被平台感知**：独立脚本，不在 smartchat 内 | 与对话系统无关 | 接入 chat 模块，对话里能触发 |

> **结论**：二开的本质是 **"把一条已验证的离线管线，接进一个已有服务化平台"**。不是从零开发，是**集成工程**。这是本产品书最重要的判断——它决定了工作量和风险都可控。

## 3. 产品形态与端到端流程

### 3.1 完整流程

```
① 上传           ② 解析 & 提取            ③ 复核
用户选 PDF   →   pdfplumber 取词级坐标  →  左右对照界面
                 ↓                         左：pdf.js 渲染原文
                 FC 引擎按六区域提取       右：条目卡片列表
                 ↓                         点条目 → 跳页 + 高亮框
                 条目 JSON（含 anchor）    状态机：待确认/采纳/剔除/存疑
                 ↓                         未覆盖语句面板（防漏）
                 本地匹配算页码/坐标         ↓
                 覆盖度校验 → 未覆盖语句   ④ RAG 填充
                                          采纳条目 → searchRag
                                          → 填充"我方是否具备"
                                           ↓
                                           ⑤ 导出
                                          强制全部确认后导出
                                          JSON / Word / Excel
```

### 3.2 界面构成

| 界面 | 内容 |
|---|---|
| **入口** | chat 页面新增"标书复核"入口（或独立路由 `/tender`） |
| **复核主界面** | 左 60% 原文阅读区（pdf.js + 高亮层 + 翻页缩放）、右 40% 清单区（条目卡片 + 进度条 + 未覆盖语句面板） |
| **导出结果** | 清单表（含已剔除项附页 + 核对声明） |

## 4. 功能需求（含验收标准）

### F1 · 文档上传与解析

| 项 | 内容 |
|---|---|
| 输入 | PDF 文件（文字版） |
| 处理 | 上传落盘 → pdfplumber 逐页取词级包围盒 → 建"字符→词"索引 → 页脚数字投票算页码 offset |
| 输出 | `ParsedDocument`（含每页 words/text/widx，offset） |
| **验收** | 上传一份真实招标文件，解析后总页数正确；offset 校准结果与人工核对一致 |

### F2 · 条款自动提取（FC 引擎）

| 项 | 内容 |
|---|---|
| 输入 | 解析后的分块文本（按六区域切分，15% overlap） |
| 处理 | **复用 chat 模块的 FC 流式引擎**，新增工具 `submit_requirements`；system prompt 注入三条铁律 + 六区域 + 易漏点清单 |
| 工具参数 schema | `items: [{ name, quote, origin, level, form, anchor }]` |
| 输出 | `RequirementItem[]`（页码与坐标由 F3 本地计算，**模型只给 quote 和 anchor**） |
| 流式反馈 | SSE 推送 `extracting` 事件（已提取 N 条 / 当前区域） |
| **验收** | 对同一份 PDF，提取条目数与人工核对偏差 = 0（强制项无遗漏）；每条都带 anchor |

> ⚠️ **设计红线**：模型**不得**输出页码。页码必须由本地字符串匹配计算——模型数不准页。

### F3 · 锚点定位与坐标计算

| 项 | 内容 |
|---|---|
| 处理 | 对每条 `anchor` 在解析文本中定位：精确匹配优先 → 失败走**字符级容错匹配**（容忍表格跨列污染，跳过量上限 0.6×锚点长+4）→ 按行合并成矩形框 |
| 异常处理 | `MISS`（未匹配）→ 条目标记 `not_found` 并在界面**标红"原文未找到"**；`AMBIG`（多处出现）→ 列出候选页供人工选定 |
| 输出 | 每条 `page` / `pagePrinted` / `rects` |
| **验收** | `verify_rects.py` 几何验证 **PASS 率 100%、SKIP = 0** |

### F4 · 覆盖度校验（防漏）

| 项 | 内容 |
|---|---|
| 处理 | 扫描全文，筛出**同时含"提供类动词"和"材料名词"**的语句 → 剔噪（网址/电话/邮箱/目录）→ 排除已被条目覆盖的 |
| 输出 | `uncovered[]`（含预计算坐标） |
| 界面 | 右栏"未覆盖语句"面板，每条三动作：定位高亮 / 加入条目（名称自动推断）/ 忽略 |
| **验收** | 噪音收敛到人工可过一遍的量级（参考值 ~70 条）；未覆盖语句的坐标定位同样精准 |

### F5 · RAG 填充"我方是否具备"

| 项 | 内容 |
|---|---|
| 输入 | 已采纳的条目（材料名称） |
| 处理 | 逐条调 `KnowledgeBaseService.searchRag(材料名称)` → 取 Top-3 → 作为"我方历史资料"填充 |
| 输出 | 条目新增 `ourSide` 字段（含引用来源） |
| 界面 | 条目卡片显示检索到的历史资料 + 引用标记 |
| **验收** | 对已在知识库中的材料（如营业执照、类似业绩合同），能检索出对应资料 |

> 这是**二开最核心的新增价值**——把"文档工具"变成"知识库驱动的 Agent"。

### F6 · 复核与导出

| 项 | 内容 |
|---|---|
| 状态机 | `待确认 / 采纳 / 剔除 / 存疑`，**导出前强制全部非"待确认"** |
| 排序 | 默认按 PDF 物理页码升序，可切"按分类"（组内仍按页码） |
| 导出 | ① 确认 JSON；② 规范 Word（封面→清单主体→已剔除项附页→核对声明）；③ Excel |
| **验收** | 未全部确认时点导出被拦截；导出文件结构完整、含剔除留痕 |

### 5.2 关键技术决策（已于 2026-10-02 拍板，锁定）

#### ✅ D1：Python 管线集成方式 = 子进程调用（已定）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 子进程调用** | NestJS `child_process.spawn('python', [...])` | 单服务部署、改动最小、复用全部既有脚本 | 需目标机装 Python 环境；进程开销 | ✅ **已采纳（一期）** |
| B. 独立 HTTP 服务 | Python 包 FastAPI，NestJS 用 HTTP 调 | 语言边界干净、可独立扩缩 | 多一个服务要起、部署变复杂 | 二期可选 |
| C. Node 重写管线 | 用 pdfjs-dist 重写定位逻辑 | 纯 Node 栈 | **会丢掉已验证的容错匹配/页码校准/几何验证** | ❌ **禁止** |

> **决策记录**：选 A。理由——"复用已验证资产"优先级高于"架构纯粹"。C 方案会被架构红线第 1 条直接拦截。
> **实施要求**：进程调用需处理 ①路径与参数转义 ②Python 环境探测（缺失时明确报错而非静默失败）③超时控制 ④stderr 捕获（Python 报错要能透传到日志）。

#### ✅ D2：复核界面形态 = 分阶段演进（已定）

| 阶段 | 做法 | 理由 |
|---|---|---|
| **阶段 1-2** | 后端调 Python 生成**单文件 HTML**，前端下载/新窗口打开 | 改动最小，先跑通链路、有可演示成果 |
| **阶段 3** | 把条目 JSON + 坐标通过 **API 返回**，用 Vue + pdf.js 重写复核界面 | 融入平台，条目能与对话/知识库联动 |

> **决策记录**：分阶段。**不在第一天重写前端**——先有能跑的成品，再谈融合。
> **演进要点**：阶段 1 的产出物不会被丢弃——它同时是 M1 的演示物料和阶段 3 的对照基准。

#### ✅ D3：数据表设计（已定）

| 表 | 用途 |
|---|---|
| `tender_document` | 上传的招标文件（id / filename / path / pageCount / pageOffset / createdAt） |
| `tender_item` | 提取的条目（id / documentId / name / quote / origin / level / form / anchor / page / rects / matchStatus / status / ourSide） |

> **决策记录**：一期建两张表，参考 `session` 模块的 TypeORM 写法。
> **实现要点**：`rects` 存 TEXT（JSON 字符串）；`tender_item.documentId` 建索引；`matchStatus` 取值 `verified | not_found`。

| **关键约束** | **必须复用 `KnowledgeBaseService.searchRag()`**，不得新写检索逻辑 |

### 阶段 5 · 导出与对话联动（0.5 天）

| 项 | 内容 |
|---|---|
| change id | `add-tender-export-and-entry` |
| 交付物 | 导出功能 + chat 入口 |

| **关键约束** | 导出内容**必须来自机器验证过的逐字引用**，AI 概括仅作标题 |

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| **准确性** | 强制项漏检率 = 0；条目必须有原文依据（无依据的条目一律删除）；几何验证 PASS 率 100% |
| **性能** | 100 页 PDF 完整流程 < 3 分钟；单文件 HTML < 8 MB（超过则降级为"数据与 PDF 分离"） |
| **兼容** | 仅支持文字版 PDF；扫描件明确告知"无法保证逐字准确"并拒绝出清单 |
| **安全** | 招标文件为内部资料，**不出本机/内网**；不引入外部 SaaS |
| **可测试** | 每个阶段必须有可自动化的验收手段（几何验证 / 语法检查 / DOM 桩测试） |

## 8. 风险与降级

| 风险 | 触发 | 应对 | 面试话术 |
|---|---|---|---|
| 扫描件 PDF | 无文本层 | 明确告知无法保证准确，请用户提供文字版 | "扫描件的识别准确率支撑不了招投标的容错度，一期不做，宁可不出错" |
| 环境缺 Python | 目标机无 Python | 阶段 0 先验证环境；必要时改为"本地生成 + 上传" | "一期是单机部署，环境是可控的" |
| 锚点 MISS | 表格跨列污染 | 已用容错匹配解决；仍有 MISS 则标红提示人工修正 anchor | "36 条从 4 条 MISS 降到 0 条，靠的是字符级容错匹配" |
| 提取漏项 | 模型遗漏 | 双门槛覆盖度校验兜底；未覆盖语句面板人工过一遍 | "我不信任模型的自觉性，靠机器校验链兜底" |
| 大文件超时 | PDF 过大 | 异步任务 + 进度推送；超 8MB 降级分离模式 | —— |

## 9. 明确不做（防跑偏清单）

> **本节是给 AI 的硬约束。** 任何一条越界都算跑偏，必须停下来问。

| # | 不做 | 理由 |
|---|---|---|
| 1 | ❌ 用户体系 / 登录 / 权限 | 一期单实例，内部工具 |
| 2 | ❌ 扫描件 OCR | 准确率不足以承担废标风险，二期 |
| 3 | ❌ 多格式支持（Word/图片） | 一期只做文字版 PDF；Word 需先转 PDF |
| 4 | ❌ 重写 pdfplumber 管线为 Node | 会销毁已验证资产 |
| 5 | ❌ 让模型输出页码 | 红线，模型数不准页 |
| 6 | ❌ 运行时前端模糊搜索定位 | 会跳错位置，坐标必须预计算 |
| 7 | ❌ 向量库升级为专业方案（Milvus/faiss） | 一期数据量小，暴力检索够用 |
| 8 | ❌ 完美 UI 样式 / 响应式 / 移动端 | 内部工具，能用即可 |
| 9 | ❌ 替换现有 FC 引擎 / 引入 LangChain 等框架 | 复用既有引擎，保持技术栈统一 |
| 10 | ❌ 云部署 / 容器化 | 本机/内网运行即可 |
