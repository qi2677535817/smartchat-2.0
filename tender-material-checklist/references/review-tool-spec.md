# 双栏复核工具规范（阶段 5 交互式交付）

本文件定义"招标文件材料清单"的交互式复核工具规范。适用于**源文档为 PDF** 的场景（已与用户确认的定位方案）。

## 一、设计目标（与用户锁定的 8 项决策）

| 决策点 | 结论 |
|---|---|
| 定位基准 | 仅 PDF，坐标级精确高亮（pdfplumber 离线预计算矩形框） |
| 复核动作 | 采纳/剔除、编辑文本与出处、标记存疑、手动新增并绑定位置 —— **全部需要** |
| Word 导出 | 双通道：① 浏览器内一键导出 .docx；② 导出确认 JSON → 交由 AI 生成规范 Word（封面/表头/分页/页码） |
| 交付形态 | 单文件离线 HTML（PDF 与数据内嵌，双击即用，可发同事） |
| 左栏渲染 | pdf.js 内嵌真实 PDF（可缩放、文字可选中） |
| 导出拦截 | 强制确认后才能导出（未确认条目拦截） |
| 剔除留痕 | Word 附"已剔除项清单"页，含剔除理由与确认人/时间 |
| 自查列 | 页面内可勾选"我方是否具备"（已有/需办理/待确认），随导出带出 |

## 二、核心机制

### 1. 坐标高亮（精准的来源）

- 用 pdfplumber 取**单词级**包围盒 `(x0, top, x1, bottom)`。
- 把条目锚点文本（anchor）与页面文本做**去空白归一化**匹配，得到字符区间，再映射回词区间。
- 按行分组（同一行的词合并为一个横向矩形），得到 1..N 个高亮矩形。
- pdf.js viewport scale=1 时坐标与 PDF 单位 1:1，`left = x0*scale`、`top = top*scale`，高亮层用绝对定位覆盖在 canvas 上。
- **禁止在运行时做模糊搜索**——搜索会跳错位置，必须在生成期算好坐标。

### 2. 双页码对照（消除错位）

招标文件常有封面页导致"PDF 物理页码"与"文档标注页码"整体错位。工具必须：

- 生成期读取页脚数字，自动推算 `offset = 物理页 - 标注页`；
- 左栏与列表同时显示"PDF 第 X 页 / 标注第 Y 页"；
- 无法识别页脚时标注为"未校准"，提示人工核对。

### 3. 两道自动质检（对应"不能少、不能错"）

- **逐条回验**：每条条目的 anchor 必须能在 PDF 中找到坐标框；找不到 → 标记 `待人工确认`，并在报告中列出（拦截幻觉条目）。
- **覆盖度校验**：扫描全文，按"**提供类动词（提供/出具/提交/须/应/加盖/盖章/附）+ 材料名词（承诺函/声明函/证书/证明/凭证/发票/扫描件…）双门槛**"筛出语句，并剔噪（网址/电话/邮箱/目录），标出**未被任何条目覆盖**的语句，输出为右栏"未覆盖语句"面板（防漏）。双门槛 + 剔噪把噪音从 500+ 收敛到 ~70 条，是人工可过一遍的量级。
- **未覆盖语句也预计算坐标**：对每条未覆盖语句，整句精确匹配优先、失败则取前缀（应对表格页跨列污染），离线算好 `rects` 与 `anchor` 一并写入 HTML，使"定位高亮"同样精准，而非运行时搜索。
- 同一 anchor 命中多页/多次 → 标记为歧义，报告列出全部命中位置供人工选定。

## 三、单文件 HTML 结构

```
review.html（约 2-3MB）
├─ <style>  双栏布局：左 60% 阅读区，右 40% 清单区（可拖拽分隔）
├─ 左栏：pdf.js canvas 渲染 + 高亮层 + 页码指示 + 缩放/翻页
├─ 右栏：分组条目列表 + 复核进度条 + 未覆盖语句面板 + 操作按钮
├─ 内嵌数据：items JSON（含坐标）+ base64 PDF + pdf.js 库
└─ <script>：pdf.js 渲染、高亮定位、条目状态机、导出逻辑
```

- pdf.js 库与 worker 均内联（worker 源码放 `<script type="text/plain">`，用 Blob URL 挂载，保证离线）；
- PDF 以 base64 内嵌，`atob` 解码为 Uint8Array 交给 pdf.js；
- 条目状态：`待确认 / 采纳 / 剔除 / 存疑`，导出前强制全部非"待确认"。
- **排序模式（默认按页码升序）**：条目默认按 PDF 物理页码升序排列，避免复核时在文档中来回跳页；另提供"按分类"一键切换（分组内仍按页码升序）。未定位条目恒定排在最末。按页码模式下每条卡片显示所属分类，避免丢失分类信息。
- **未覆盖语句面板**：每条语句在生成期已预计算高亮坐标，卡片提供三个动作——「定位高亮」（跳页 + 框出原文）、「加入条目」（一键补录为条目，名称自动从材料名词推断）、「忽略」；已处理项从计数中扣除，勾选"显示已处理"可回看与恢复。

**状态色值约定**（暖米白大地色系、适配 light 主题，改版时不得随意变更）：

| 状态 | 卡片样式 | 说明 |
|---|---|---|
| 待确认 | 边框 `#D8CFBC`、背景 `#FFFFFF` | 默认白卡；边框须在白底上可见 |
| 采纳 | 边框 `#8FAF6B`、背景 `#E7F0D6` | 柔和橄榄绿，**必须明显区别于白底**，一眼可辨已采纳区 |
| 剔除 | 虚线边框 + 背景 `#F1EDE3`、`opacity:.68` | 弱化但文字仍可读（不再用 `.55`，过浅伤眼） |
| 存疑 | 边框 `#D9A23F`、背景 `#FBF0D8` | 暖黄提示，需明显可见 |

**对比度基线（硬约束，勿回退）**：

- 正文/引文 ≥ 4.5:1：主文字 `#2E2A24`、引文 `#33302B`、次要信息 `#5B554A`、提示 `#6B6459`；
- **禁止使用 `#98907F` 这类浅灰做小字**（对比度仅约 3:1，实测导致长时间阅读眼疲劳，已全面替换）；
- 右栏面板背景 `#F6F2E9` 比卡片 `#FFFFFF` 略深，用层次区分卡片而非仅靠极浅边框；
- 徽章（强制/评分/条件项/编制项/可选）文字统一加深到 `#8F3529`/`#7A5410`/`#33546F`/`#7A4C31`/`#5D5648` 并加粗；
- 可点元素一律 `cursor:pointer` + 150ms `transition`，`button:focus-visible` 有 2px 描边。

> 注：采纳底色曾用 `#FCFDF9`（近白，肉眼难辨）→ `#EAF2DC` → 现值 `#E7F0D6`，逐步加深；其余三态同步加深。

## 四、条目数据结构

```json
{
  "id": 1,
  "cat": "A 资格证明文件",
  "name": "营业执照等证明材料",
  "quote": "投标人为企业（包括公司、合伙企业、个人独资企业）的，提供有效的营业执照",
  "origin": "第四章资格审查办法前附表第1项；第六章格式八（一）1-1",
  "level": "强制",
  "form": "扫描件或电子证照",
  "note": "按我司类型为企业→营业执照",
  "anchor": "提供有效的营业执照",
  "page": 35, "pagePrinted": 34,
  "rects": [[x0, top, x1, bottom]],
  "status": "待确认"
}
```

`anchor` 由录入者指定（应短、唯一、不跨页）；`rects` 由生成脚本计算，不得手写。

## 五、产出与验收

1. 交付 `*_材料清单复核.html`（单文件离线）；
2. 交付前必须实测：至少抽查 3 条条目点击后跳转页正确、高亮框覆盖原文无偏移；
3. 人工复核完成后导出：① `.docx`（浏览器）；② 确认 JSON（交 AI 生成规范 Word）。
4. Word 结构：封面信息 → 清单主体（按七大类分组，组内按 PDF 页码顺序）→ 已剔除项附页 → 核对声明。

## 六、边界与降级

- 扫描件 PDF（无文本层）→ 无法生成坐标，降级为"仅图片 + 人工手动定位"，明确告知用户；
- DOCX 源文件 → 先转 PDF 再走本流程（Word 无固定页码，不做 HTML 锚点方案）；
- 单文件超过 8MB → 提示可改为"PDF 与数据分离 + 本地服务"模式。

## 七、已踩过的技术坑（务必遵守，实测总结）

1. **表格页跨列交错（最关键）**
   pdfplumber 在表格页会把同一视觉行不同列的文字拼接在一起，锚点会被外来文字打断，例如
   `提供有效的税务登记证（多证合一的提供营` + `依法缴纳税收的详见第六章投标文件2` + `业执照），或者…`。
   因此**禁止用简单子串查找（`in` / `find`）**定位锚点，必须用字符级**容错匹配**（允许跳过干扰字符，跳过量上限约 0.6×锚点长度）。已实测：改用容错匹配后，36 条条目定位从 4 条 MISS 变为 0 条 MISS。

2. **页码双轨制必须校准**
   含封面/扉页的招标文件，物理页与文档标注页常整体错位。用页脚数字投票推算
   `offset = 物理页 − 标注页`（实测 79 页文档投票 78 次命中 offset=1，可靠）。
   界面必须同时显示两套页码，否则用户按清单页码翻不到位置——这正是"页码不精准"投诉的根因。

3. **占位符替换必须用不冲突记号**
   生成器若用 `__ITEMS__` 这类记号并调用 `str.replace`（全局替换），会把注入代码里的
   `window.__ITEMS__=__ITEMS__;` 左侧一并替换，导致 JS 语法错误、页面白屏。
   改用 `@@ITEMS@@` 等 **不与注入代码变量名重合** 的记号，并在生成后校验无残留记号。

4. **交付前必须做的四项自检**（缺一不可）
   - `verify_rects.py` 几何验证：PASS 率要求 100%（把高亮框区域裁出来提取文字反查原文）；条目与"未覆盖语句"两套 rects 都要验；
   - 抽出内联 `<script>` 用 `node --check` 验证语法（pdf.js 与应用脚本各一次）；
   - 检查 `window.__ITEMS__` / `__UNCOVERED__` / `__PROJECT__` 注入的 JSON 可解析；
   - 前端逻辑最小 DOM 桩测试（排序 / 加入条目 / 名称推断），见坑 8。

5. **沙箱内无法启动浏览器时的替代验证**
   agent-browser / Playwright 在受限沙箱内可能无法派生 Chromium 进程。此时不要卡住，
   改用"几何验证 + 语法验证 + 交付给用户在真实浏览器打开确认"的组合策略；交付时明确
   告知用户哪部分（渲染/点击/导出）需要其本机浏览器实测。

6. **client-side 兜底能力**
   新增条目的坐标由浏览器端 `getTextContent()` 用 scale=1 viewport 现算（`Util.transform` 转坐标），
   算法与 Python 端一致，保证人工补录的条目也能精确高亮。

7. **统计口径：SKIP 不等于 PASS**
   `verify_rects.py` 早期把"无定位（SKIP）"也计入 PASS 数，导致报告出现
   `共 74 条，PASS 74 条` 的假象（实为 73 PASS + 1 SKIP）。凡统计通过率，必须把
   PASS / SKIP / FAIL 三类分开计数，SKIP 单独列明——否则"防漏"会变成"漏了还报全绿"。

8. **前端逻辑要用最小 DOM 桩离线跑通，不能只做语法检查**
   `node --check` 只能证明语法合法，证明不了"排序真的对、加条目真的生效"。做法：
   抽出内联应用脚本，剥离真实数据注入行（`window.__ITEMS__=…` 会覆盖测试数据，是个隐蔽陷阱），
   在 Node 里用最小 `document`/`window` 桩执行，断言 `renderList()` 产出的卡片顺序、
   `ucAdd()` 后条目数与状态、`guessName()` 输出。实测据此发现了两处真实缺陷。

9. **新增条目的出处字段必须处理"未定位"分支**
   `pgLabel(null)` 会渲染出 `PDF 第 null 页 ／ 标注第 -1 页`。凡是可能为空的页码，
   都要先判空再拼接（如 `u.page ? pgLabel(u.page) : '页码待核对'`）。
