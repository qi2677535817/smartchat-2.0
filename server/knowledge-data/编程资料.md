变量是代码的容器，也是程序员思维的具象化。很多新手写代码时习惯用 a、b、tmp、data 这种“糊弄自己”的名字，当时写得快，两周后回头看，连自己都要花十分钟才能猜出 tmp 里到底装的是什么。起名这件事，本质上是给逻辑贴标签。见名知意不是一种风格，而是一种责任。布尔变量用 is、has、should 开头（isActive、hasPermission），数组用复数形式（users、items），函数用动词开头（getUser、validateInput），这些约定不是教条，而是为了降低阅读成本。类型同样不能含糊，TypeScript 里别动不动就 any，Python 里也别假设变量永远是字符串。该用常量就用 const，这不仅是防止误赋值，更是在向读代码的人宣告：这个值在语义上是不可变的。清晰的变量命名 + 严格的类型约束，本身就是一种不需要额外文档的注释。

函数是把重复逻辑打包的利器，但很多人的函数写着写着就变成了“大杂烩”。一个函数既解析请求、又查数据库、又处理业务逻辑、最后还负责格式化返回结果，几百行代码揉在一起，改一处崩三处。好的函数应该只做一件事，并且把这件事做到清晰可见。如果一个函数需要塞七八个参数，说明你的抽象出了问题，要么是把多个职责揉在了一起，要么是需要引入一个配置对象（DTO/VO）来承载这些参数。参数越少，函数的可测试性越高，出错的概率越低。函数名同样要诚实，不要叫 processData 这种模糊的名字，要叫 filterActiveUsers 或 calculateMonthlyRevenue，让调用者一眼就知道它不会偷偷发请求或写文件。

调试是很多初学者的短板，大家最习惯的方式就是满屏 print 或 console.log，但这其实是效率最低的手段。print 只能看到某一个时刻的状态，而断点调试能让你看到整个调用栈：是谁调用了这个函数？参数在每一步是如何变化的？异常是从哪一层抛出来的？学会在 VS Code 或 Chrome DevTools 里下断点、单步执行、观察变量，是进阶的必经之路。遇到怪问题时，排查顺序也很重要：先怀疑数据，再怀疑逻辑，最后才怀疑环境。90% 的 Bug 都是数据不符合预期导致的——接口返回了 null、数组是空的、字段名拼错。先打印或观察输入数据，确认数据没问题，再去走查逻辑分支，最后才去考虑 Node 版本、依赖冲突或操作系统差异。

最实用的技巧，往往最朴素：改一行，测一行。很多人喜欢一口气写一百行代码再运行，结果一跑就报错，面对满屏红字根本不知道是哪一行引起的。好的习惯是写几行就跑一次，甚至用 TDD 的方式先写测试再写实现。这样即使出错，你也知道问题一定出在刚才改的那几行里。另外，出错了先读报错信息，而不是盯着代码发呆。报错信息里通常有错误类型、出错文件和行号，有时候还有堆栈提示。学会读报错，就像学会看地图，能直接带你找到问题现场，而不是在原地瞎猜。

最后，写好注释。很多人觉得“代码即文档”，但代码只能告诉读者“做了什么”，很难解释“为什么这么做”。那些看似多余的注释，往往是用来解释业务背景、特殊处理或性能考量的。比如：// 这里必须用 for 循环而不是 map，因为需要提前 break；// 这个字段为空是因为老系统兼容逻辑，2024 年后可删除。这些注释不是为了解释代码，而是为了保存当时做决策时的上下文。三个月后的你，或者半年后接手你代码的人，最想感谢的，就是现在愿意多写几行注释的你。

写代码不是写给自己看的，是写给未来的自己和团队看的。变量名清晰一点，函数短一点，调试耐心一点，注释诚实一点，代码质量自然就高一点。
